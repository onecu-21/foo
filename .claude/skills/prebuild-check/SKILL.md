# 빌드 전 검사와 릴리스 빌드

저장소 루트에서 아래 네 단계를 **이 순서대로** 실행합니다. 앞 단계가 실패하면 뒤 단계는 실행하지 않습니다. 포맷이나 lint가 깨진 상태로 테스트와 릴리스 빌드에 시간을 쓰는 것은 낭비이고, 실패 원인도 흐려지기 때문입니다.

| 단계 | 명령 | 확인하는 것 |
| --- | --- | --- |
| 1. 포맷 | `cargo fmt --check` | rustfmt 규칙 위반 |
| 2. Lint | `cargo clippy --workspace --all-targets -- -D warnings` | 경고를 포함한 모든 clippy 지적 (테스트 코드 포함) |
| 3. 테스트 | `cargo test --workspace` | 단위 테스트와 `tests/cli.rs` 통합 테스트 |
| 4. 빌드 | `cargo build --release` | 릴리스 바이너리 `target/release/foo(.exe)` |

각 명령은 별도로 실행해 단계별 결과를 구분할 수 있게 합니다. 테스트와 릴리스 빌드는 몇 분 걸릴 수 있으니 타임아웃을 넉넉히(예: 10분) 잡습니다.

**Windows에서는 Git Bash가 아니라 PowerShell로 실행합니다.** Git Bash의 `PATH`에서는 Git의 `/usr/bin/link.exe`(파일 링크 유틸리티)가 MSVC 링커보다 먼저 잡힙니다. 그래서 테스트가 내부에서 `rustc`로 풀이를 컴파일할 때 `linking with link.exe failed ... /usr/bin/link: extra operand` 오류로 실패합니다. 이 오류가 보이면 코드 문제가 아니므로 PowerShell에서 다시 실행합니다.

## 실패했을 때

실패한 단계에서 멈추고, 출력 전체를 붙여 넣지 말고 원인이 되는 부분(파일:줄, 오류 메시지, 실패한 테스트 이름)만 추려서 보고합니다.

- **포맷 실패**: `cargo fmt`로 고칠 수 있다고 알립니다. 사용자가 고쳐 달라고 했거나 수정 작업 중이었다면 `cargo fmt`를 실행한 뒤 1단계부터 다시 검사합니다.
- **clippy 실패**: 지적된 위치와 lint 이름을 보고합니다. 고치는 경우 `#[allow(...)]`로 덮지 말고 코드를 수정합니다. `-D warnings`는 경고를 허용하지 않겠다는 의도이기 때문입니다.
- **테스트 실패**: 실패한 테스트 이름과 assert 메시지를 보고합니다. 통합 테스트는 `rust` 언어로 초기화하고 실제로 Rust 풀이를 컴파일하므로, `rustc`를 찾지 못한다는 오류라면 코드 문제가 아니라 환경 문제일 수 있다고 구분해서 알립니다. 한 테스트만 다시 돌릴 때는 `cargo test --test cli <이름 일부>`를 씁니다.
- **릴리스 빌드 실패**: Windows에서 `target\release\foo.exe`에 접근할 수 없다는 오류(액세스 거부, 다른 프로세스가 사용 중)가 나면 `foo`가 실행 중이거나 VS Code 작업이 잡고 있을 가능성이 큽니다. 코드 문제가 아니므로 그 프로세스를 종료하라고 안내합니다.

수정한 뒤에는 고친 단계만이 아니라 **1단계부터 다시** 실행합니다. 수정이 다른 검사(예: 포맷)를 깨뜨릴 수 있기 때문입니다.

## 결과 보고

모두 통과하면 짧게 보고합니다.

```
✅ fmt · ✅ clippy · ✅ test (N passed) · ✅ release build
바이너리: target/release/foo.exe
```

실패가 있으면 어느 단계에서 멈췄는지, 원인, 그리고 실행하지 않은 단계를 명시합니다. 실행하지 않은 단계를 통과했다고 쓰지 않습니다.
